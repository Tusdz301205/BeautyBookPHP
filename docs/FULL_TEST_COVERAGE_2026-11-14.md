## Active surfaces and role boundaries

All React paths below are relative to the default `/beautybook` basename; APIs are under `/api/v1`. `routes/web.php` defaults to modern React when `BEAUTYBOOK_LEGACY_UI=false`; enabling it loads `routes/legacy.php` instead. `phpunit.xml` currently forces legacy mode true, so individual modern tests that override config/environment are especially important. `SourceSurfaceTest` boots with false; `BookingRecipeFlowTest` sets modern config false for the guarded booking behavior.

| Actor / scope | Implemented active entry points and restrictions |
| --- | --- |
| Guest | `/`, `/explore`, branch/service/staff detail, `/for-business`, login/register/recovery/verification/invitation. Can read public catalog and public staff calendars; `/book` requires a customer login and preserves return location. Signed-in `/` redirects to the selected workspace. |
| CUSTOMER / self | `/book`, `/customer/book`, appointments/detail, recurring, notifications, messages, wallet, vouchers, reviews, benefits (saved services), security, profile. Operational accounts require a separate customer account. Data and money must stay self-scoped. |
| BUSINESS_OWNER / tenant | `/salon` overview, onboarding, services/combos, appointments, staff/detail, new/setup branch, promotions/vouchers, reviews/AI, profile, payments, operations, notifications, security/account, branch preview; permission and business-approval gates apply. Owner is explicitly redirected away from `/salon/stats`, `/salon/audit`, `/salon/incoming-ownership`. |
| RECEPTIONIST / exact branch | Shared salon shell with permission-based landing; scoped appointment/counter/check-in, payment, staff/calendar and messaging capabilities. Must not inherit tenant-wide authority from another branch or unrelated secondary role. |
| STAFF / assigned work and live grants | Shared salon shell, assigned booking/item information and permitted self detail/calendar/reviews. Historical per-item lifecycle tests exist, but modern aggregate completion must use its current allowed actions; do not expect legacy item commands on the active screen. |
| PLATFORM_ADMIN / platform | `/admin` overview, salons, branch/business detail, users/detail, appointments, payments, reports, moderation, audit, notifications, settings, security/profile. Platform booking views are not operational appointment controls. |
| Multi-role / multi-business | Login challenge chooses a real context. Permissions union only live grants within that context; role expiry/revocation must affect subsequent API, media, socket and push access. Test both receptionist+staff same branch and grants across different branches. |

### Available code that is not an ordinary active modern screen

* `/customer/privacy` renders `UnavailableFeature`; API privacy reads and preference update remain, but POST data-request/export creation is registered only in legacy mode. Privacy export tests must not be reported as a working modern privacy UI.
* Waitlist join/offer/accept/cancel and loyalty rules/earn/redeem are implemented in legacy operations routes; `CustomerBenefits` currently contains saved services only. No modern waitlist/loyalty route appears in `App.jsx`.
* Booking move/resize/assign, add/update item and GET/PATCH item actual-time APIs are inside `LegacyBookingSurface`, returning 404 in modern mode. Modern recipe bookings use aggregate lifecycle; `/book/:step` redirects to `/book`, and `/book/success` redirects to appointments. Old step page files do not prove active routing.
* `/salon/staff/schedule` redirects to appointments; `/salon/deposit-settings` redirects to payments. Customer ownership query redirects to incoming ownership (or salon home for current owner).
* Ownership creation/legal/payout versions are active in the permission-gated salon Operations panel, and incoming acceptance has a salon route. `/admin/ownership` redirects home; `/admin/violations` redirects salons; `/admin/compliance` redirects salons review view. `AdminOwnership.jsx` and `AdminViolations.jsx` existing on disk do not establish active direct routes. Full transfer execution/verification APIs exist; discover whether the current merged admin review surface exposes their controls before claiming end-to-end accessibility.
* `/salon/stats` and `/salon/audit` are permission-routed for applicable non-owner contexts; explicit owner redirect takes precedence. Reports/audit backend coverage does not prove owner access to those URLs.
* Wallet and salon/admin payment workspaces default enabled but `VITE_FINANCE_WORKSPACE=false` replaces them with unavailable UI. This frontend flag does not itself remove backend finance routes. Wallet lab/public top-up and deposit features have independent backend policy flags.
* Treatment-package and platform-statement APIs and panels are modern finance functionality. Invoice request/issue/replacement/void workflows are covered through legacy finance routes, with no invoice API declarations in `beautybook-finance.php`.
* Push OAuth/FCM stand-in endpoints are registered only when the local/testing trial sink is explicitly enabled. They are not real Google FCM delivery.
